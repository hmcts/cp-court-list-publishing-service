1. At a glance

Everyone

Courts publish court lists: the schedule of hearings for a court on a given day. Some lists are for the public, some for the press, and some for court staff, prisons and other justice partners.

The Court List Publishing Service is the part of Common Platform that:

01

Collects

Hearing data from the Listing and Progression services.

02

Transforms

Into the publication format, removing unsafe content and checking it against a schema.

03

Publishes to CaTH

The GOV.UK service where the public and the press view court lists.

04

Stores a PDF

In Azure Blob Storage so staff can download exactly what was published.

05

Generates downloads

On-demand PDF or Word versions of many list types for staff and partners.

06

Publishes SJP lists

National Single Justice Procedure lists (public and press) to CaTH.

07

Tracks status

Publish and file status for every list, with errors recorded for support.

QuestionShort answer
What triggers a publish?A user (via the Common Platform UI) or a system user calls the publish API.
Is publishing instant?The request is accepted immediately; the work (data fetch, CaTH send, PDF) runs in the background a few moments later.
Which lists go to CaTH?Magistrates' Standard and Online Public lists, plus the SJP public and press lists (full and delta, English and Welsh).
Where do PDFs go?Azure Blob Storage, downloadable via /api/files/download/{fileId}.
What if I publish the same list twice?The existing record for that court, date and list type is reused and re-processed. The latest attempt overwrites the previous one.
Who can do what?Controlled by user groups — see Security & access.

2.4 Business rules

#Rule
BR-1A court list is identified by court centre + publish date + list type. There is at most one tracking record per combination.
BR-2A publish request must have start date = end date (a single day).
BR-3Re-publishing an existing list resets its status to REQUESTED and runs the whole process again; the newest attempt is what CaTH shows.
BR-4A late failure never hides an earlier success: if a list already reached CaTH (or its PDF was stored), a slower failing attempt does not overwrite SUCCESSFUL with FAILED.
BR-5CaTH displays a magistrates' list from the moment it is published until 23:59 UTC on the publish date.
BR-6SJP lists are national: they have no court centre. They are displayed for 24 hours from publication.
BR-7Public lists are sent with sensitivity PUBLIC; standard and press lists are sent as CLASSIFIED.
BR-8Welsh courts use Welsh/bilingual templates and the CaTH language WELSH.
BR-9Prison lists can only be downloaded through the dedicated prison endpoint, by prison-list roles.
BR-10Data (status records, PDFs, CaTH payload copies) older than the retention period (default 90 days) is deleted by the cleanup job.
BR-11Text that the Azure Web Application Firewall would block (by default ..\ and ../) is stripped from published content, so a legitimate list is not rejected at the gateway.

2.5 The publishing journey (business view)

2.6 SJP list variants

The SJP system sends four list types, each in English or Welsh, so there are eight daily publications.

  • Full lists contain every ready case; delta lists contain only the changes since the last send.
  • Press lists include extra detail (e.g. reporting restrictions per offence) and are CLASSIFIED.

3.5 Key design decisions

DecisionWhy
API-first — controllers implement interfaces from a separate spec artifactOne contract shared with consumers; Pact verifies it. API changes start in the spec repo.
Asynchronous processing via task-manager-serviceCaTH, document generation and upstream queries can be slow; the user gets an immediate REQUESTED response.
Tasks always complete (COMPLETED), with failures recorded on the status rowAvoids blind retries that could double-publish; failures are visible and alertable (PUBLISHING_FAILED).
Shared status table for standard and SJPOne place to track all publications; SJP rows have no court centre or file (enforced by CHECK constraints).
Sanitise then schema-validate before sendingCaTH and the Azure WAF reject bad payloads; catching that early gives clearer errors.
Pluggable CourtListPublisherThe real CaTHPublisher goes through APIM; the integration profile swaps in StubCourtListPublisher that posts to WireMock.
Optional Azure storageBeans that need storage are conditional, so the service can run without it (e.g. some local setups).

4. Key flows, step by step

DevelopersQA

4.1 Standard publish (STANDARD / ONLINE_PUBLIC)

  • The task fetches the payload twice: once with applications (for CaTH) and once without (for the PDF).
  • If CATH_PUBLISHING_ENABLED=false, the CaTH step is skipped and the publish status stays REQUESTED. The PDF is still generated.
  • A failure in one step does not stop the next step; each is recorded separately.

5. Status lifecycle

Everyone

Each tracked list has two independent statuses: publish status (did it reach CaTH?) and file status (was the PDF stored?). SJP rows have only a publish status.

StatusMeaningWhat to do
REQUESTEDAccepted, work pending or in progress. For publish status it also means CaTH publishing is disabled in this environment.Wait, then re-check. If it stays here, check CATH_PUBLISHING_ENABLED and the job executor.
SUCCESSFULReached CaTH / PDF stored (fileId set, publish_count incremented).None.
FAILEDThe step failed. The full stack trace is in publish_error_message / file_error_message.Investigate the error; re-publish once fixed.
RuleCourtListStatusUpdater.shouldRecord refuses exactly one transition — writing FAILED over SUCCESSFUL — so attempts finishing out of order cannot hide a list that is live.

Other protections

  • Authz and audit filters are off by default (CP_CLP_AUTHZ_ENABLED, CP_CLP_HTTP_AUDIT_ENABLED, CP_CLP_AUDIT_ENABLED) and switched on per environment.
  • Outbound CaTH calls use Azure AD client-credential tokens; no secrets are stored in the repo (secrets are mounted at /mnt/secrets/rpe/).
  • Log messages built from user input are encoded with the OWASP encoder (Encode.forJava).
  • Published content is HTML-stripped and WAF-sanitised before it leaves the service.
  • CI runs CodeQL, PMD, an OWASP ZAP baseline scan and a secrets scanner.

11.4 How to inspect results

  • Status: GET /api/court-list-publish/publish-status?courtListId=…, or query the DB (court_list_publish_status) on localhost:55432 (db/user/password courtlistpublishing).
  • CaTH payload: blob {courtListId}-cath.json in Azurite, or the WireMock request journal (http://localhost:8089/__admin/requests).
  • PDF: GET /api/files/download/{fileId} or blob {fileId}.pdf.
  • Logs: docker logs CP_CLP_app_it; search for PUBLISHING_FAILED.
